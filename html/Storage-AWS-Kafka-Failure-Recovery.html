Storage platform on AWS: lowest cost, Kafka, and every failure drilled

The object storage platform (Go API, nine workers, a Postgres outbox, ClamAV, S3 and tenants' own clouds) deployed on AWS for about $90 a month, with Kafka as the event backbone. The short version

~$90 / month

On demand, Mumbai, at launch scale: two Graviton instances, a small RDS Postgres, S3 and CloudFront, no NAT gateway. About $70 with a 1-year Savings Plan and RDS reservation.

Postgres is the record, Kafka is the road

Every event is committed to the outbox in the same transaction as the change. If Kafka disappears the workers' database polls keep the work moving and the reconciler republishes what was never consumed. That is why one cheap broker is safe at launch.

Kafka replaces SQS, not NATS

There is no NATS in the code. The queue is SQS (ElasticMQ locally) behind one MessageQueue interface; a Kafka adapter plugs in there: 5 topics, keyed by aggregate, one consumer group each.

Postgres is the one thing to protect

Leases, outbox, inbox, webhooks and dead letters all live there. Start Single-AZ with point-in-time recovery; Multi-AZ is the first upgrade. Make the pool size configurable: 11 processes × 21 connections overruns a small RDS.

Hybrid by design

Tenants bring their own S3, R2, GCS or Azure. A tenant's cloud going down only stalls that tenant; records never fall back to another bucket. Workers need internet egress, so public subnets beat a $40 NAT gateway.

Fail closed on malware

If ClamAV is down, uploads are held in quarantine, never promoted. A restart and a requeue release them.

            Kafka in place of the queue

            About NATS. The code has no NATS: the workers use SQS FIFO queues (ElasticMQ locally) behind interfaces.MessageQueue (internal/interfaces/job_queue.go:65-85). Kafka goes behind that same interface, so the outbox, inbox, reconciler and dead-letter tools stay as they are.

            Producer and consumer settings

            • Key = GroupKey (aggregate_type:aggregate_id), so one aggregate stays on one partition in order.
            • Producer: idempotent, acks=all, wait for the ack; event_id and DedupKey in headers.
            • Consumer: auto-commit off; commit a partition's offset only when every earlier offset is settled (groups run concurrently).
            • Extend becomes a no-op: the inbox lease already fences. Poll on its own goroutine so long jobs (up to 30 min) never exceed max.poll.interval.ms.
            • Attempt count from the inbox (rec.Attempts); a <topic>.dlq read by the reconciler mirrors the SQS DLQ drain.
            • Stats from consumer-group lag.

            Broker settings for the lowest-cost start

            • Apache Kafka 4.x in KRaft mode, one combined broker and controller, heap 768 MB, on the data node's own 30 GB gp3 volume.
            • Replication factor 1 at launch, safe only because the outbox is the record; move to 3 brokers, RF 3, min.insync.replicas=2 at the next stage.
            • auto.create.topics.enable=false; topics created by a migration step.
            • Retention 7 days, below the inbox retention (keep 14 days) so a replay is always recognised.
            • lz4 compression; messages carry IDs only (outbox payload is capped at 64 KiB).
            • Go client: a pure-Go library such as franz-go keeps the static distroless build.

            The absolute floor, and why not

            One t4g.large running everything, Postgres in Docker with WAL archiving to S3: about $52 a month. It saves $40 but puts Postgres, the platform's only coordinator, on a disk you must back up and restore yourself. Use it for staging, not for tenants' data.

            Why not managed Kafka at this stage

            MSK with two kafka.t3.small brokers is about $67 a month before storage, and MSK Serverless bills a cluster-hour on top. With the outbox carrying correctness, a single self-run broker gives the same safety for about $8 of a shared instance. Move to MSK when the team would rather pay than patch.

            Deployment layout

            Network

            • One VPC, two public subnets (two AZs, ready for stage 1), no NAT gateway. Workers reach tenant clouds and webhook receivers over their public IPs, through the code's own network guard.
            • Security groups: app node 443 from the CloudFront managed prefix list only; Kafka 9092 and clamd 3310 from the app node only; RDS 5432 from both nodes only; no SSH (SSM Session Manager).
            • S3 gateway endpoint; IMDSv2 required.

            Compute

            • ECS on EC2 (the control plane is free): one service per binary, restart on exit, rolling deploys, task IAM roles (S3 uses the default chain, no keys).
            • Kafka as a systemd service on the data node with its data on a separate EBS volume; clamd as an ECS service with a TCP health check and freshclam.
            • Auto Scaling groups of min 1, max 1 per node: a failed instance is replaced from the launch template.
            • One-off ECS tasks for migrate, event-admin, identity-admin.

            Data

            • RDS PostgreSQL 17, PITR 7 days, Performance Insights free tier, max_connections sized to the pools.
            • S3: one platform bucket (quarantine/, manifests/, packs/) and a serving bucket for assets/, default SSE-KMS, versioning, AbortIncompleteMultipartUpload after 7 days, Block Public Access.
            • CloudFront: API origin (with an origin secret header) and the serving bucket through Origin Access Control; signed URLs via the existing signer.

            Secrets, deploys, watching

            • SSM Parameter Store SecureString (KMS) for DATABASE_URL, STORAGE_CREDENTIAL_KEYS, the CloudFront key and signing keys.
            • CI builds one distroless arm64 image per binary to ECR, then updates the ECS services.
            • Alarms: RDS CPU and connections, Kafka consumer lag, outbox PENDING age, scanner_up, dead letters count, 5xx at CloudFront, instance status checks.
